## Wider Context / Higher Goal

Дві цілі одночасно, задані автором:

1. **Безпечно привести API до ладу** — зафіксувати контракт, щоб далі виправити розбіжності між документацією та кодом і доробити те, що обіцяно, але не реалізовано.
2. **Отримати базу для нового функціоналу** — поточний стан потрібен як відправна точка, бо далі плануються нові можливості `ElasticModel`.

Задум бібліотеки (зі слів автора, 2026-10-10): структура оголошується **повною**, як справжня, хоча під капотом може бути динамічною й не містити частини задекларованих полів. Альтернатива — оголошувати кожне поле як `Optional`, і тоді IDE та статичні аналізатори вимагають постійних перевірок `is not None`, хоча розробник знає, що поле на місці. Повна декларація прибирає цей шум. Плата за це свідома: **ризик доступу до незавантаженого поля лежить на розробнику**, а не на типах. Головний цільовий сценарій — projection у MongoDB, де заради оптимізації з БД дістають не всі поля, але працювати хочуть із повною оголошеною формою.

Принцип автора (2026-10-15): **весь функціонал pydantic лишається як є, а `ElasticModel` його лише розширює.** Для того самого класу й тих самих даних поведінка `BaseModel` — еталон; розходження допустиме лише як свідоме розширення, описане в README. Правило для роботи над кодом записане в `CLAUDE.md` проєкту.

Уточнення автора того ж дня: «`ElasticModel()` по суті створює `BaseModel` як є, але тип створеного об'єкта повертає `ElasticModel` для подальшого користування його методами». Код, налаштований на `BaseModel`, після переходу працює без змін, а нове доступне окремими методами `elastic_*`. Модель, створена через `elastic_create`, — уже не те саме, що `BaseModel`, тому розходження для неї допустимі як описані розширення.

## Context

Пакет опублікований на PyPI під іменем `gostmodels`, версія 0.2.4, ліцензія MIT — verified via: `pyproject.toml:6-14`, 2026-10-10. Файл `README.md` оголошений як `readme` пакета, тобто він і є сторінкою опису на PyPI та фактичним публічним контрактом — verified via: `pyproject.toml:12`, 2026-10-10.

Проблема, що породила цю задачу: **публічний контракт описує поведінку, якої в коді немає**. Розходження зачіпають головну заявлену гарантію бібліотеки, обидва приклади коду та метадані пакування.

#### Група 1. Незреалізована гарантія та її справжні межі

**Розбіжність 1 — головна заявлена гарантія не реалізована.**
`README.md:14` оголошує `NotLoadedFieldError` як ключову можливість, `README.md:62` імпортує його в Quick start, `README.md:111` показує його підняття. У коді цього імені немає ніде, крім докстрінгів і коментарів — verified via: `grep -rn "NotLoadedFieldError" gostmodels tests` → лише `gostmodels/elastic_model.py:5,14,195,230`, 2026-10-10. Класу не існує, `raise` відсутній, `__getattr__` не перевизначений — verified via: `grep -rn "__getattr__" gostmodels` → жодного входження, 2026-10-10.

Наслідки, перевірені емпірично 2026-10-10:
- `gostmodels.NotLoadedFieldError` → `AttributeError: module 'gostmodels' has no attribute 'NotLoadedFieldError'`, тобто рядок імпорту з Quick start не виконується
- Доступ до оголошеного незавантаженого поля → `AttributeError: 'Doc' object has no attribute 'b'`, а не власна помилка бібліотеки

Механіка, через яку це відбувається: при `defaults=False` `elastic_create` видаляє дефолтні поля з інстансу через `delattr`, тому незавантажене поле просто відсутнє, і далі працює штатна обробка pydantic — verified via: `gostmodels/elastic_model.py:303-305`, 2026-10-10.

**Розбіжність 2 — гарантія не може діяти для полів, чиє ім'я збігається з атрибутом батьківського класу.**
`README.md:215` формулює гарантію без винятків: «Accessing an unloaded declared field raises NotLoadedFieldError». Але механізм перехоплення читання спрацьовує лише тоді, коли звичайний пошук атрибута не знайшов нічого. Поле з іменем наявного методу повертає цей метод: `json` і `copy` дають `<bound method BaseModel.json>` і `<bound method BaseModel.copy>` замість помилки — verified via: прогін проби, 2026-10-12. Поле з іменем власної властивості обгортки ламає конструктор ще раніше: `AttributeError: property 'elastic_extra' … has no deleter` — verified via: прогін проби, 2026-10-12.

Важливе полегшення: pydantic сам попереджає про це на етапі оголошення класу — `UserWarning: Field name "json" in "Shadow" shadows an attribute in parent "ElasticModel"` — verified via: прогін проби, 2026-10-12. Тобто розробника попереджають, і виправляти треба **формулювання гарантії**, а не поведінку.

**Розбіжність 3 — гарантія не діє для дефолтних полів.**
При `defaults=True` поле, якого не було в даних, читається й повертає дефолт, хоча `elastic_is_loaded` для нього `False` — verified via: прогін проби, 2026-10-11. Тобто формулювання з `README.md:215` і після реалізації гарантії лишиться неточним: «незавантажене» і «відсутнє в інстансі» — не те саме.

#### Група 3. Хибно описана семантика

**Розбіжність 8 — README обіцяє, що дефолти позначаються як завантажені, і це суперечить коду та явному тесту.**
`README.md:212` твердить: `apply_defaults=True` «applies `default`/`default_factory` to missing fields **and marks them as loaded**». Факт: при `defaults=True` дефолтне поле присутнє, але не вважається завантаженим — `elastic_is_loaded("flag")` → `False` — verified via: прогін проби, 2026-10-11. Цю саму поведінку закріплює тест із промовистим іменем `test_defaults_true_keeps_defaults_but_not_loaded`, що асертить `u.elastic_is_loaded("flag") is False` — verified via: `tests/test_elastic_model.py:166-182`, 2026-10-11.

Це **єдине місце, де рішення «істиною є README» непридатне**: виконати обіцянку README означає зламати наявний тест, тобто порушити NFR-1. Рішення автора від 2026-10-11: істина тут — код, правиться README. Обґрунтування: «loaded» означає «прийшло з джерела даних», а дефолт звідти не приходив; злиття цих випадків зробило б `elastic_is_loaded` безкорисним, бо саме їх і треба відрізняти.

**Розбіжність 9 — твердження про повне наслідування `BaseModel` не відтворюється.**
`README.md:10` та `README.md:31` обіцяють: «Fully inherits the behavior of `pydantic.BaseModel`: all methods and functionality. Just replace `BaseModel` with `ElasticModel`». Факт: модель із `@computed_field` ламає конструктор — `elastic_create({"x": 2})` на класі з обчислюваним полем падає з `AttributeError: 'WithComputed' object has no attribute 'doubled'` — verified via: прогін проби, 2026-10-11. Причина: `model_dump()` віддає й обчислювані поля, яких немає в переліку переданих користувачем, тому код намагається їх видалити — verified via: `gostmodels/elastic_model.py:293-305`, 2026-10-11. **Закрито 2026-10-17**: після FR-10 `elastic_create` не проходить по `model_dump()`, і модель з `@computed_field` будується, зокрема з частковими даними — verified via: прогін проби й тест `test_elastic_create_supports_computed_field`, 2026-10-17.

#### Група 4. Аліаси

**Розбіжність 10 — мапінг аліасів залежить від конфігу, і README про це не каже.**
Мапінг застосовується лише коли в конфігу моделі ввімкнено `populate_by_name` — verified via: `gostmodels/elastic_model.py:251,257-259`, 2026-10-10. Клас `User` у Quick start оголошує `Field(alias="_id")` без `model_config` — verified via: `README.md:70-76`, 2026-10-10. Розділ «Defaults and config» рекомендує лише `extra='ignore'` та `revalidate_instances='never'` і про аліаси не згадує — verified via: `README.md:240-245`, 2026-10-10.

Перевірено на трьох варіантах конфігу 2026-10-10:

| Конфіг моделі | Доступ до `.id` |
|---|---|
| без `model_config` (як у README) | `AttributeError`; значення потрапляє в `elastic_extra` як `{'_id': 'u1'}` |
| `populate_by_name=True` | працює, повертає `'u1'` |
| `validate_by_name=True` | `AttributeError` |

Третій рядок — проблема сумісності з актуальним ключем. Актуальний документований API pydantic — це `validate_by_alias` (типово `True`) і `validate_by_name` (типово `False`); `populate_by_name` у розділі документації про аліаси не згадується — verified via: Context7, документація pydantic, 2026-10-11. Формального статусу «deprecated» документація не стверджує, рантайм-попередження при вживанні старого ключа не з'являється.

На рівні класу pydantic 2.11.7 розгортає старий ключ у новий: клас зі `populate_by_name=True` має в `model_config` обидва, клас із `validate_by_name=True` — лише новий — verified via: прогін проби на `model_config` класів, 2026-10-11. Старий ключ лишається валідним і вживається в наявних тестах у трьох місцях — verified via: `grep -rn "populate_by_name" tests/` → `tests/test_elastic_model.py:38,403,409`, 2026-10-12. У README він не вживається ніде.

#### Група 6. Внутрішній стан, що протікає в публічний

**Розбіжність 14 — публічна властивість віддає службове поле.**
`elastic_loaded_fields` повертає технічне `_elastic_finished` разом із користувацькими полями: `{'a', '_elastic_finished'}`, і `elastic_is_loaded('_elastic_finished')` → `True` — verified via: прогін проби, 2026-10-10. Причина: `__setattr__` спершу викликає `super().__setattr__`, тому охоронна перевірка вже бачить `True` і додає до набору саме це ім'я — verified via: `gostmodels/elastic_model.py:311,399-406`, 2026-10-10. Протікає не лише службовий прапорець: будь-який приватний атрибут, присвоєний користувачем після побудови, теж потрапляє в набір — verified via: прогін проби, `{'x', '_private', '_elastic_finished'}`, 2026-10-11.

**Розбіжність 15 — публічна властивість віддає живий внутрішній набір без копії.**
`elastic_loaded_fields` повертає сам внутрішній `set`, а не його копію — verified via: `gostmodels/elastic_model.py:321-323`, 2026-10-12. Тобто користувач може змінити внутрішній стан моделі, і `elastic_is_loaded` почне брехати. Рішення автора від 2026-10-12: втягнути в scope, бо документувати властивість, через яку можна зіпсувати внутрішній стан, означає закріпити це в контракті PyPI.

#### Група 7. Метадані пакування

**Розбіжність 16 — пакет не оголошує залежностей.**

#### Група 8. Знахідки код-рев'ю реалізації (2026-10-14)

Рев'ю гілки `feat/em-1-elastic-model-contract` дало 9 зауважень, розбір кожного — у розділі «Review». Тут лише ті, що стосуються публічного контракту, плюс три знайдені в головній сесії.

**Розбіжність 19 — без конфігу аліаси працюють дзеркально до pydantic.**
pydantic типово приймає вхідний ключ за аліасом і не приймає за іменем поля: `validate_by_alias` типово `True`, `validate_by_name` типово `False` — verified via: Context7, документація pydantic 2.11, 2026-10-14. `elastic_create` робить навпаки: без ключів конфігу `{'_id': 'x'}` потрапляє в `elastic_extra`, а читання `.id` дає `NotLoadedFieldError`, тоді як `{'id': 'x'}` приймається — verified via: прогін проби, 2026-10-14. Причина: мапінг аліасу на поле вмикає лише ключ, що дозволяє ім'я поля — verified via: `gostmodels/elastic_model.py:272-280`, 2026-10-14.

Розбіжність 10 описувала той самий механізм, але попередня редакція виправила його через README (ключ конфігу в прикладі), а не через поведінку. Тому обіцянка «просто заміни `BaseModel` на `ElasticModel`» (`README.md:10`) не діє для жодної моделі з аліасом: модель, що працювала на `BaseModel`, після заміни втрачає дані. Рішення автора від 2026-10-14: правила аліасів мають збігатися з pydantic.

**Розбіжність 20 — `validate_by_alias=False` ігнорується.**
При `ConfigDict(validate_by_name=True, validate_by_alias=False)` pydantic відкидає `{'_id': 'x'}` з `ValidationError`, а `elastic_create` приймає й заповнює `.id` — verified via: прогін проби, 2026-10-14.

**Розбіжність 21 — два методи валідують з різними параметрами, і після узгодження аліасів це стає дефектом.**
`elastic_is_valid` валідує payload з іменами полів без `by_name=True`, а `elastic_get_validated_model` — з ним — verified via: `gostmodels/elastic_model.py:366` vs `:396`, 2026-10-14. pydantic без `by_name` відкидає payload з іменем аліасованого поля — verified via: прогін проби, `ValidationError: Field required` для `{'id': 'x'}`, 2026-10-14. Доки модель без ключів конфігу не могла завантажити аліасоване поле, різниця не проявлялася, і попередня редакція винесла її за межі scope. Після виправлення розбіжності 19 така модель завантажуватиме поле за аліасом, і `elastic_is_valid` повідомлятиме, що воно відсутнє. Тому різниця повертається в scope як умова FR-4.

**Розбіжність 22 — анотації методів не розв'язуються в рантаймі.**
Виправлення розбіжності 18 перенесло імпорт `Self` під `TYPE_CHECKING` (`gostmodels/elastic_model.py:45-48`). Ламаються інструменти, що читають анотації в рантаймі; рев'ю називає `validate_call`, sphinx-autodoc-typehints і typeguard, окремо їх не перевіряли. pydantic сам вимагає `typing-extensions>=4.12.2` — verified via: `importlib.metadata.requires("pydantic")`, 2026-10-14.

**Розбіжність 23 — моделі, створені не через `elastic_create`, не знають своїх завантажених полів.**
Екземпляр з `elastic_get_validated_model`, екземпляр зі звичайного конструктора та вкладені моделі, створені валідацією pydantic, мають порожній `elastic_loaded_fields`, і присвоєння в них не відстежується — verified via: прогін проби, `validated → []`, `User(...) → []`, 2026-10-14. Причина: перелік і прапорець відстеження заповнює лише `elastic_create` — verified via: `gostmodels/elastic_model.py:330-332`, 2026-10-14.

**Розбіжність 24 — `elastic_extra` віддає живий внутрішній словник.**

**Розбіжність 25 — параметри конструктора не доходять до вкладених моделей.**

Наслідок: `User.elastic_create({...}, defaults=True)` заповнює дефолти лише на верхньому рівні, а читання дефолтного поля вкладеної моделі дає `NotLoadedFieldError` — verified via: прогін проби, 2026-10-14. README описує `defaults=True` без обмеження рівнем вкладеності — verified via: `README.md:197`, 2026-10-14. Знайдено в головній сесії.

**Розбіжність 26 — вкладений `BaseModel` при `validate=False` приймає і аліас, і ім'я незалежно від конфігу.**

При `validate=True` той самий вкладений `BaseModel` розбирає pydantic за його конфігом, тобто правила залежать від прапорця валідації. Знайдено в головній сесії; виправлення — ідея агента, погоджена автором 2026-10-14.

#### Група 9. Аудит відповідності `BaseModel` (2026-10-15)

Після принципу автора «`ElasticModel` лише розширює `BaseModel`» (Wider Context) агент чистим контекстом прогнав 47 сценаріїв. Еталоном у кожному був той самий клас, оголошений на `BaseModel`. Результат однаковий на pydantic 2.11.7 і 2.14.1. Щоб відрізнити регресії від давніх дефектів, ті самі проби прогнано на комітах `69c3b6b` і `master`.

Звичайний шлях pydantic (конструктор, `model_validate`, валідатори, аліаси, `model_dump`, копії, JSON schema) збігається з `BaseModel` усюди, крім `==`. Решта розходжень — у `elastic_create` і методах перевірки. Шість вердиктів аудиту і чотири властивості pydantic, на які спирається FR-10, перевірені в головній сесії власною пробою. Розбір — у розділі «Review». У дужках — номери пунктів аудиту.

**Розбіжність 27 — `==` для моделей зі звичайного шляху розходиться з pydantic (9.1).**
`E(a=1) == E(a=1, b=2)`, де `b` має дефолт `2`, дає `False`, а на `BaseModel` — `True` — verified via: прогін проби, 2026-10-15. Так само для `model_construct` і frozen-моделі. Причина: pydantic у `__eq__` порівнює `__pydantic_private__` — verified via: `inspect.getsource(BaseModel.__eq__)` і Context7, migration guide pydantic, 2026-10-15. After-валідатор обліку (історія 9.0) пише туди різні набори для різних вхідних даних. Регресія незакомічених змін: на `69c3b6b` і `master` результат `True`.

**Розбіжність 28 — власний облік завантажених полів розходиться зі станом моделі (7.2, 7.3, 6.3, 1.3, 11.5).**
- Поверхнева копія (`model_copy()`, `copy.copy`) ділить набір з оригіналом: присвоєння в копії позначає поле завантаженим в оригіналі, хоча читання там дає `NotLoadedFieldError`.
- Після `model_copy(update={'y': 5})` поле читається, але `elastic_is_loaded('y')` дає `False`, хоча pydantic додає його в `model_fields_set`.
- Присвоєння через сетер `@property` додає в облік ім'я властивості — verified via: прогін проби, `['a', 'double']`, 2026-10-15. Для моделей зі звичайного шляху це регресія.
- Після `model_construct(x=...)` `elastic_is_loaded('x')` дає `False`.
- Текст помилок вкладених моделей у `TypeAdapter`/`Union` містить ім'я after-валідатора: `nullable[function-after[_elastic_track_validated(), N]]` замість `nullable[N]`. Регресія, косметична.

Спільна причина — бібліотека веде власний набір паралельно зі станом pydantic, і кожен шлях, що змінює модель в обхід її перехоплювачів, ці два стани розводить.

**Розбіжність 29 — перевірка моделі підміняє значення поля ключем із `model_extra` (13.1, 13.2).**
Поле `uid` з аліасом `_id`, `extra='allow'`. pydantic для `{'_id': 'REAL', 'uid': 'FAKE'}` дає `uid == 'REAL'` і `model_extra == {'uid': 'FAKE'}`, а `elastic_get_validated_model()` тієї самої моделі дає `uid == 'FAKE'` — verified via: прогін проби, 2026-10-15. Причина: payload складається як `__dict__ | model_extra`, тобто ключ `model_extra` перекриває поле, а валідація з `by_name=True` приймає його як значення поля. Після `del m.uid` `elastic_is_valid()` дає `(True, [])` — регресія: на `69c3b6b` було `(False, ['_id'])`.

**Розбіжність 30 — глибока перевірка залежить від налаштувань серіалізації (13.4, 6.2).**
Payload глибокої перевірки будується через `model_dump()`, тому валідна модель отримує хибне «невалідно»: при `serialize_by_alias=True` — `['uid']` (регресія), при `Field(exclude=True)` — `['secret']`, при `@field_serializer` — `['x']`, при `@computed_field` і `extra='forbid'` — `['dbl']`. При `extra='allow'` обчислюване поле потрапляє в `model_extra` копії. З тієї ж причини `elastic_create` на моделі з `serialize_by_alias=True` падає з `AttributeError`: цикл по `model_dump()` бачить аліаси замість імен полів — знайдено код-рев'ю 2026-10-15, зауваження 2.

**Розбіжність 31 — `elastic_create(validate=True)` пропускає дані, які pydantic відкидає (1.5, 10.3, 10.4, 14.2, 14.4, 4.2).**
Значення валідується `TypeAdapter`, побудованим лише з анотації (`get_type_hints`), тобто без `FieldInfo` і без конфігу моделі:
- обмеження з форми `x: int = Field(gt=0)` не діють: `-1` приймається — verified via: прогін проби, 2026-10-15;
- `ConfigDict(strict=True)` не діє: `'5'` стає `5` — verified via: прогін проби, 2026-10-15;
- ігноруються `str_strip_whitespace`, `str_to_lower`, `coerce_numbers_to_str`, `use_enum_values`, а з `arbitrary_types_allowed` побудова падає з `PydanticSchemaGenerationError`;
- generic-модель `G[int]` не враховує параметр: `'abc'` приймається;
- локальні класи з `from __future__ import annotations` падають з `NameError` у `get_type_hints`;
- при `defaults=True` дефолт поля з `validate_default=True` не валідується: `"7"` лишається рядком.

Давнє. README обіцяє, що значення «validated by Pydantic».

**Розбіжність 32 — `elastic_create` падає на frozen-моделі (10.2).**
`frozen=True`, поле з дефолтом, `defaults=False`: `ValidationError: Instance is frozen` — verified via: прогін проби, 2026-10-15. Причина: незавантажений дефолт прибирається через `delattr`, а pydantic забороняє його на frozen-моделі. Давнє.

**Розбіжність 33 — `validation_alias` обходить валідацію і змінює правила ключів (2.2, 2.3).**
Таблиця ключів не знає ключів `validation_alias`, тому передає їх у `model_construct` як невідомі, а той заповнює ними поле без валідації: `x: int = Field(0, validation_alias=AliasChoices('_x'))`, дані `{'_x': 'not-int'}`, `defaults=True` → `x == 'not-int'`, поле не позначене завантаженим — verified via: прогін проби, 2026-10-15. Крім того, для поля з `validation_alias` таблиця приймає ім'я поля і `alias`, які pydantic відкидає. Давнє.

**Розбіжність 34 — при `extra='allow'` ключ, що не заповнив поле, не потрапляє в `model_extra` (3.2).**
pydantic кладе в `model_extra` кожен такий ключ: заборонене ім'я, заборонений аліас і ім'я, що програло аліасу — verified via: прогін проби, 2026-10-15. `elastic_create` кладе його лише в `elastic_extra`. Знайдено код-рев'ю 2026-10-15 (зауваження 7), аудит підтвердив. Давнє, форма змінилася в історії 8.0.

**Розбіжність 35 — `extra='forbid'` не діє в `elastic_create` (3.3).**
pydantic відкидає невідомий ключ з `extra_forbidden`, а `elastic_create` кладе його в `elastic_extra`, і `elastic_is_valid()` дає `(True, [])`. Рішення автора 2026-10-15: це свідоме розширення — `elastic_extra` зберігає невідомі ключі за будь-якого значення `extra`. Описується в README.

**Розбіжність 36 — `elastic_get_validated_model` губить `elastic_extra` (13.5).**
`elastic_extra == {'zz': 2}` у джерелі стає `{}` у копії. Рішення автора 2026-10-15: копія переносить `elastic_extra`.

**Розбіжність 37 — моделі з однаковими даними, але різним `elastic_extra`, нерівні (9.2).**
Рішення автора 2026-10-15: так і має бути. Модель з `elastic_create` уже не те саме, що `BaseModel`, тому `==` враховує `elastic_extra`. Моделей зі звичайного шляху це не зачіпає, бо їхній `elastic_extra` завжди порожній. Описується в README.

**Розбіжність 38 — помилка `elastic_create` не називає поле і показує лише першу (1.6).**
Для `{'a': 'x', 'b': 'y'}` pydantic дає `ValidationError` з заголовком моделі й двома помилками з `loc` `('a',)` і `('b',)`. `elastic_create` дає заголовок `int`, одну помилку і порожній `loc`. Давнє. Рішення автора 2026-10-15: поза scope, окрема фіча; README описує обмеження.

**Розбіжність 39 — README мовчить про межі `elastic_create` і перебільшує дію параметрів (1.4, 11.3, 11.4).**
- `@field_validator` і `@model_validator` в `elastic_create` не запускаються; докстрінг про це каже, README — ні.
- Часткові дані в полі `Optional[N]`, `N | None`, `Union` чи дискримінованому `Union` дають `ValidationError`, а при `validate=False` такі поля лишаються `dict`. README обіцяє, що вкладені моделі будуються.
- README пише, що `defaults` і `strict_validate` діють на кожному рівні вкладеності. Насправді вони не діють на поля `Optional`/`Union`, а `strict_validate` — ще й на вкладений `BaseModel` при `validate=False` — знайдено код-рев'ю 2026-10-15, зауваження 3–5.

Давнє.

### Prior Art (зовнішній огляд)

Перевірено на запит автора: чи існує готове рішення для цього задуму. **Не існує.** Екосистема ділиться на два підходи, і жоден не дає потрібної семантики.

**Підхід «зробити поля Optional»** — суперечить головній цілі, бо аналізатор бачить `T | None` і знову вимагає перевірок:

- `pydantic-partial` — `create_partial_model()`, поля стають nullable з `None` за замовчуванням
- `pydantic-strict-partial` — найближчий за валідацією: поля не nullable, валідація жива, але додається `None`-дефолт, тож відсутнє поле читається як `None`, а не падає
- `metantic`, `pydantic-tooltypes` — `Partial(User)` / `Partial[User]`, той самий підхід
- `pydantic-partials` — архітектурно найближчий: сентинел `Missing` замість дефолту, але доступ до відсутнього поля повертає сентинел, а не кидає помилку, і тип стає `T | Missing`

**Підхід «окрема модель на кожну проекцію»** — Beanie `.project(ProjectionModel)`, мейнстрім для MongoDB. Форма всередині кожної моделі повна й без `Optional`, але доводиться підтримувати окремий клас на кожну проекцію і втрачаються методи канонічної моделі.

**У самому pydantic** готового механізму немає: `experimental_allow_partial` стосується розбору неповного вхідного JSON, а не проекцій. Відкрите issue pydantic #5326 «Replace `__fields_set__` with an `Unset` type» ставить рівно цю ціль — анотації «not-None but not required», які проходять mypy — і досі залишається issue.

**Prior art, що підтверджує семантику:** SQLAlchemy `defer(Col, raiseload=True)` та `load_only(..., raiseload=True)` дають повну оголошену модель зі свідомо незавантаженими атрибутами, доступ до яких кидає `InvalidRequestError`. Мотивація в їхній документації збігається з мотивацією цього проєкту: завантажити рівно те, що потрібно операції, і зробити будь-який неочікуваний доступ помилкою замість тихого обходу. Отже `NotLoadedFieldError` — не екзотика, а pydantic-аналог усталеного `raiseload`.

Джерела цього розділу — зовнішні, позначки `verified via:` до них не застосовні.

**Огляд механізмів pydantic для коду бібліотеки (2026-10-17, на вимогу автора «не вигадувати велосипед»).** Перевірено пробами на pydantic 2.11.7 і 2.14.1: дослідження агента в чистому контексті, а ключові висновки повторено в головній сесії.

Не підходить:
- `validate_assignment` — запускає `@field_validator` і `@model_validator(mode='after')`, не будує частковий вкладений dict, не приймає аліас.
- `experimental_allow_partial` — дозволяє лише обрізаний кінець даних; пропущене поле посередині дає `missing`.
- Sentinel `MISSING` — у 2.11 його немає, а в новіших версіях він вимагає анотації `X | MISSING` у кожному полі.
- `model_construct` — приймає ім'я, аліас і `validation_alias` без правил конфігу й нічого не валідує.
- `model_validate(instance)` з ревалідацією або `from_attributes` — на екземплярі того самого класу повертає його без змін, а `revalidate_instances` не задається на виклик.
- `model_validator(mode='wrap')` на базовому класі — валідатори користувача з підкласу стають зовні нього й спрацьовують в `elastic_create`.
- «Двійник» core-схеми (переписування `__pydantic_core_schema__` з sentinel-дефолтами й підставним класом) — працює (134 з 147 тестів без змін), але тримається на непублічній формі схеми та на знятті валідаторів через збіг bound-методів. Відкинуто автором як важка конструкція.

- `__get_pydantic_core_schema__` з `core_schema.with_info_wrap_validator_function` — штатний спосіб обгорнути схему типу (Context7), і часткові вкладені моделі в `Optional`/`Union` з ним працюють. Але обгортка міняє звичайний шлях pydantic: на 2.11.7 `model_validate(..., by_alias=False, by_name=True)` перестає приймати ім'я поля, а на всіх версіях мітка гілки в помилках `Union` стає `function-wrap[...]` замість імені класу — verified via: проба й наявні тести паритету, 2026-10-18. Відкинуто: порушує правило «`ElasticModel` лише розширює `BaseModel`».

Висновок: публічного механізму pydantic, що будує часткові моделі й не змінює звичайного шляху, немає. Тому таблиця ключів, адаптер поля, обхід вкладених моделей і обхід стану для перевірки лишаються власними (рішення автора 2026-10-18).

## Problem Statement

**Who**: розробник, що підключив `gostmodels` з PyPI і читає `README.md` як опис контракту.

**What**: публічний контракт описує поведінку, якої немає. Перший приклад не виконується, а шість із дев'яти його документованих виводів хибні; другий приклад правдивий, але не перевіряється нічим. Головна заявлена гарантія не реалізована, тому помилка доступу до незавантаженого поля не відрізняється від опечатки в імені атрибута. Пакет не оголошує залежності від pydantic, непрацездатний на версіях нижче 2.11 і обіцяє підтримку Python, на якому не імпортується.

**Why**: саме незреалізована гарантія робить свідомий компроміс бібліотеки неприйнятним. Ризик доступу до незавантаженого поля покладено на розробника, і єдина компенсація — щоб порушення було очевидним. Зі `AttributeError` воно не очевидне: та сама помилка виникає від опечатки, від перейменування поля й від реально незавантаженого поля. Розробник не може ні відрізнити ці випадки, ні перехопити саме потрібний.

**When**: при першій же спробі скористатися пакетом за інструкцією, і далі — при кожній обробці помилки доступу до поля.

## Goals

### Primary Goal

Публічний контракт і код описують одну й ту саму поведінку. Там, де вони розходяться, істиною є документація — обіцяне реалізується, а не викреслюється. Виняток зафіксовано окремо: Розбіжність 8 (обіцянка README суперечить наявному тесту). Розбіжність 9 була другим винятком, доки FR-10 не прибрав її причину (2026-10-17).

### Secondary Goals

- Доступ до незавантаженого поля відрізняється від доступу до неоголошеного — розробник може перехопити саме перший випадок.
- Гарантія описана з її справжніми межами, а не як беззастережна.
- Обидва приклади коду містять усі потрібні їм передумови явно й перевіряються автоматично.
- Контракт не ламається від переходу користувача на актуальні ключі конфігу pydantic.
- Правила аліасів збігаються з pydantic, тож заміна `BaseModel` на `ElasticModel` не втрачає даних.
- Встановлений із PyPI пакет працює: залежності оголошені з правдивими межами, оголошена версія Python досяжна.
- Публічні властивості не дають зіпсувати внутрішній стан моделі, а перелік завантажених полів правдивий для будь-якого способу створення моделі.
- Параметри головного конструктора діють на всіх рівнях вкладеності.
- Модель, створена звичайним шляхом pydantic, поводиться як `BaseModel`: бібліотека не тримає для неї власного стану (2026-10-15).
- `elastic_create(validate=True)` валідує кожне значення за тими самими правилами поля, що й pydantic (2026-10-15).

## Requirements

### Functional Requirements

1. **FR-1**: Бібліотека надає власний тип помилки для доступу до оголошеного поля, відсутнього в інстансі, і експортує його з кореня пакета під іменем, яке вже вживає README.
   - **Priority**: High
   - **Rationale**: це головна заявлена гарантія пакета і єдина компенсація за свідомо перенесений на розробника ризик. Без неї компроміс бібліотеки не має сенсу: порушення контракту неможливо ні відрізнити, ні перехопити.
   - **Dependencies**: механізм перехоплення доступу до атрибутів у pydantic v2.

2. **FR-2**: Доступ до поля, не оголошеного в моделі, зберігає поточну поведінку — нова помилка стосується лише оголошених полів.
   - **Priority**: High
   - **Rationale**: інакше нова помилка приховає справжні опечатки, тобто розв'яже одну проблему й створить дзеркальну.
   - **Dependencies**: FR-1.

3. **FR-3**: Новий тип помилки успадкований від штатної помилки доступу до атрибута, а всі три межі гарантії задокументовані.
   - **Priority**: High
   - **Rationale**: у репозиторії є 5 асертів, що очікують саме штатну помилку при доступі до незавантаженого поля — `tests/test_elastic_model.py:121,125,200,358,369` — verified via: `grep -n "pytest.raises(AttributeError)" tests/test_elastic_model.py`, 2026-10-11. Без успадкування прогін падає, тобто це умова виконання NFR-1, і коштує вона лише вибору базового класу.
   - **Три межі, які треба назвати** (усі перевірені емпірично): перевірка наявності атрибута повертає «немає», а читання зі значенням за замовчуванням повертає це значення — обидва способи глушать порушення контракту; поле з іменем атрибута батьківського класу гарантії не отримує (Розбіжність 2); дефолтне поле при `defaults=True` читається (Розбіжність 3). Беззастережне формулювання гарантії обіцяє більше, ніж механізм може дати.
   - **Dependencies**: FR-1.

4. **FR-4**: Вхідні ключі зіставляються з полями за правилами pydantic. Аліас приймається, якщо це дозволяє `validate_by_alias` (типово так). Ім'я аліасованого поля приймається, якщо це дозволяє `validate_by_name` або старий `populate_by_name` (типово ні); обидва ключі читаються незалежно. Поле без аліасу приймається за іменем завжди. Ті самі правила діють для вкладеного `BaseModel` при `validate=False`, а `elastic_is_valid` валідує з тими самими параметрами, що й `elastic_get_validated_model`.
   - **Priority**: High
   - **Rationale**: `README.md:10` обіцяє, що заміна `BaseModel` на `ElasticModel` зберігає поведінку, а дзеркальні правила аліасів (Розбіжність 19) порушують цю обіцянку з втратою даних. Старий ключ читається й далі, бо він валідний і на ньому тримаються наявні тести (`tests/test_elastic_model.py:38,403,409`). Незалежне читання обох ключів не залежить від того, чи розгортає pydantic один у другий. Однакові параметри валідації у двох методах — умова цієї вимоги (Розбіжність 21), а однакові правила для вкладеного `BaseModel` прибирають залежність результату від прапорця `validate` (Розбіжність 26).
   - **Breaking change**: значення за іменем аліасованого поля без ключів конфігу тепер потрапляє у сховище невідомих полів. Крім того, `elastic_is_valid` називає відсутнє аліасоване поле іменем поля, а не аліасом (`'id'` замість `'_id'`) — так само, як помилки `elastic_get_validated_model` — verified via: прогін проби після реалізації 8.7, 2026-10-14. Версія 0.3.0 ще не опублікована, тому зміни входять у неї (NFR-4).
   - **Dependencies**: немає.

5. **FR-5**: Публічні властивості віддають лише користувацькі дані й не дають змінити внутрішній стан моделі; перелік завантажених полів правдивий для будь-якого способу створення моделі.
   - **Priority**: High
   - **Rationale**: **передумова FR-6**. Документувати ці властивості, доки вони віддають службове поле й живий внутрішній стан, означає зафіксувати дефекти в контракті PyPI; пізніше виправлення стало б breaking change. Сховище невідомих полів має той самий дефект, що й перелік (Розбіжність 24). Модель, створена валідацією, зараз вважає незавантаженим усе (Розбіжність 23), тобто `elastic_is_loaded` бреше саме після повної перевірки моделі.
   - **Scope note**: втягнуто чотири речі — відсікання службових імен бібліотеки, копія переліку, копія сховища невідомих полів і заповнення переліку для моделей, створених валідацією. Копія сховища поверхнева: верхні ключі захищені, вкладені значення спільні з моделлю. Для моделі, створеної валідацією, завантаженими вважаються поля, що були у вхідних даних валідації. Тому поле, яке у вихідній моделі заповнив дефолт, у копії з `elastic_get_validated_model` рахується завантаженим: копія отримує його як звичайні дані.
   - **Dependencies**: немає.

6. **FR-6**: Метадані пакування відповідають дійсності: оголошена залежність від pydantic із нижньою межею, не нижчою за ту, яку вимагає код; оголошена мінімальна версія Python досяжна, а сумісність із нею не ламає розв'язання анотацій у рантаймі.
   - **Priority**: High
   - **Rationale**: це той самий клас дефекту, що й розбіжності README — публічний контракт описує неправду, лише в іншому файлі. Без оголошених залежностей чистий `pip install` дає пакет, який не імпортується; код уже вимагає pydantic 2.11, а оголошена підтримка Python 3.10 недосяжна. Перше виправлення сумісності з 3.10 зламало `typing.get_type_hints` для публічних методів (Розбіжність 22).
   - **Рівень підтримки (рішення автора 2026-10-17)**: офіційно підтримується Python 3.11+. `requires-python` лишається `>=3.10`: 3.10 не заблокований і працює на ризик користувача. README називає це й відоме обмеження 3.10 з обходом (Out of Scope). Причина: на 3.10 `elastic_create` падає на `children: list["Node"]`, бо pydantic лишає рядок усередині вбудованого generic нерозв'язаним у `model_fields` — verified via: прогін проби на cpython-3.10.20, pydantic 2.11.7, 2026-10-17. На коміті 69c3b6b падіння таке саме, тобто це не регресія EM-1.
   - **Dependencies**: немає.

7. **FR-7**: `README.md` приведений у відповідність до коду в дванадцяти місцях: підпис головного конструктора з усіма іменами параметрів; перелік публічного API з документованими типами повернення; атрибут відстеження завантажених полів; розділ про рекомендований конфіг з правилами аліасів; позначка keyword-only у підписах; твердження про позначення дефолтів завантаженими; формулювання гарантії з трьома її межами; твердження про повне наслідування `BaseModel`; тіло першого прикладу; обірвана лапка у другому прикладі; копія сховища невідомих полів і завантажені поля моделей, створених валідацією; дія параметрів конструктора на вкладені моделі.
   - **Доповнення 2026-10-15 — ще вісім місць**: (13) при `extra='forbid'` невідомий ключ потрапляє в `elastic_extra`, і це розширення; (14) `==` враховує `elastic_extra`; (15) копія з `elastic_get_validated_model` переносить `elastic_extra`; (16) `@field_validator` і `@model_validator` в `elastic_create` не запускаються; (17) часткові дані в полях `Optional`/`Union` не підтримуються; (18) помилка `elastic_create` повідомляє лише перше невалідне значення і без шляху поля; (19) дія `defaults` і `strict_validate` на вкладені моделі описана з її межами; (20) при `extra='allow'` ключ, що не заповнив поле, потрапляє ще й у `model_extra`.
   - **Priority**: High
   - **Rationale**: README — сторінка пакета на PyPI і фактичний контракт; хибний підпис у ньому призводить до помилки виклику, а хибний вивід у прикладі — до неправильних очікувань. Місця 13–15 — свідомі розширення, а за правилом автора розширення допустиме, лише коли воно описане в README. Місця 16–19 — межі, які автор вирішив назвати, а не виправляти в EM-1.
   - **Dependencies**: FR-1, FR-3, FR-4, FR-5, FR-9, FR-10–FR-14 — текст описує вже узгоджену поведінку.

8. **FR-8**: Обидва приклади коду README виконуються у складі тестового набору, причому перевірка асертить документовані виводи, а не лише відсутність виключень.
   - **Priority**: High
   - **Rationale**: шість із дев'яти дефектів першого прикладу — саме хибні значення, а не падіння. Перевірка, що підтверджує лише виконуваність, пройде зеленою при README, який і далі бреше. Другий приклад зараз правдивий, але не перевіряється нічим — тобто може розійтися з кодом тим самим шляхом, яким розійшовся перший.
   - **Dependencies**: FR-1, FR-4, FR-5, FR-7.

9. **FR-9**: Параметри `defaults` і `strict_validate` головного конструктора діють на всіх рівнях вкладених `ElasticModel`, включно з елементами контейнерів.
   - **Priority**: High
   - **Rationale**: README описує `defaults=True` без обмеження рівнем вкладеності, а фактично параметр діє лише на верхньому рівні (Розбіжність 25). Розробник, який увімкнув дефолти, отримує `NotLoadedFieldError` на вкладеному дефолтному полі без жодної підказки про причину.
   - **Межі (2026-10-15)**: параметри доходять до вкладених `ElasticModel` у прямих полях і в контейнерах. На поля `Optional`/`Union` вони не діють, бо такі поля `elastic_create` не будує (Out of Scope). Межу «`strict_validate` не діє всередині вкладеного `BaseModel` при `validate=False`» знято 2026-10-18 (історія 22): `strict_validate` вмикає валідацію і там, як для прямого поля. README описує саме ці межі (FR-7, місце 19), а не «кожен рівень вкладеності» (Розбіжність 39).   - **Dependencies**: немає.

10. **FR-10**: Для моделі, створеної звичайним шляхом pydantic, `ElasticModel` не зберігає власного стану. Облік завантажених полів обчислюється на кожен запит зі стану pydantic: поля з `model_fields_set`, присутні в інстансі, плюс ключі `model_extra`, що не є іменами полів. Єдиний власний стан моделі — `elastic_extra`, який заповнює лише `elastic_create`.
    - **Priority**: High
    - **Rationale**: принцип автора 2026-10-15 — «`ElasticModel()` по суті створює `BaseModel` як є». Власний набір у приватних атрибутах ламає `==` (Розбіжність 27), а облік, що йде паралельно зі станом pydantic, розходиться з ним на копіях і особливих шляхах створення (Розбіжність 28). Якщо обчислювати облік зі стану pydantic, обидва дефекти зникають разом: розходитися більше нічому.
    - **Перевірені властивості pydantic**: `model_construct` кладе в `model_fields_set` лише передані поля; присвоєння й `model_copy(update=...)` додають поле; `del` не прибирає поле з `model_fields_set`, але прибирає з інстансу — verified via: прогін проби, 2026-10-15. Тому формула правдива і для `elastic_create` (той будує модель через `model_construct`), і для моделі, з якої видалили поле.
    - **Ключі `model_extra`, що збігаються з іменем поля**, до обліку не входять: інакше після FR-14 заборонений ключ `'id'` позначив би незавантажене поле `id` завантаженим.
    - **Обчислювані поля (2026-10-17)**: без проходу по `model_dump()` `elastic_create` будує модель з `@computed_field`, тож Розбіжність 9 закрита, а виняток прибирається з README. Обчислюване поле, що читає незавантажене поле, дає `NotLoadedFieldError`; те саме дає `model_dump()`, бо серіалізує обчислюване поле — verified via: прогін проби, 2026-10-17.
    - **Перегляд рішення автора**: 2026-10-14 автор обрав для обліку after-валідатор (tech-design, Trade-offs). Ця вимога його замінює, а з ним і прапорець завершення та облік у перехоплювачах присвоєння й видалення.
    - **Dependencies**: немає.

11. **FR-11**: Методи перевірки (`elastic_is_valid`, `elastic_get_validated_model`) будують payload з поточного стану моделі, тобто з `__dict__` і `model_extra`, а не через серіалізатор. Ключ `model_extra`, що збігається з іменем поля, у payload не потрапляє. Копія з `elastic_get_validated_model` отримує `elastic_extra` джерела і такі ключі `model_extra` на всіх рівнях вкладеності.
    - **Priority**: High
    - **Rationale**: серіалізатор застосовує налаштування виводу (`serialize_by_alias`, `exclude`, `@field_serializer`, `@computed_field`), і валідна модель отримує хибне «невалідно» (Розбіжність 30). Ключ `model_extra` з іменем поля під час перевірки заповнює це поле (Розбіжність 29). Перенесення `elastic_extra` — рішення автора 2026-10-15 (Розбіжність 36). Ключі `model_extra` з іменем поля переносяться окремо, бо в payload їм місця немає, а без них копія валідної моделі не дорівнювала б джерелу.
    - **Шляхи помилок** лишаються іменами полів (FR-4).
    - **Dependencies**: немає.

12. **FR-12**: `elastic_create(validate=True)` валідує кожне значення за правилами поля pydantic: анотація й обмеження `FieldInfo` разом із конфігом моделі. `strict_validate=False` не скасовує суворість, задану конфігом. При `defaults=True` дефолт поля з `validate_default` теж валідується.
    - **Priority**: High
    - **Rationale**: README обіцяє, що значення «validated by Pydantic», а невалідні дані проходять мовчки (Розбіжність 31). Рішення автора 2026-10-15 — виправити в EM-1.
    - **Dependencies**: немає.

13. **FR-13**: `elastic_create` працює на моделі з `frozen=True`. Ключ `validation_alias` не заповнює поле в обхід валідації, а для поля з `validation_alias` ім'я та `alias` приймаються за правилами pydantic.
    - **Priority**: High
    - **Rationale**: Розбіжності 32 і 33; рішення автора 2026-10-15 — виправити в EM-1. Читання значення за `validation_alias` лишається поза scope, тому такий ключ іде в `elastic_extra`, як і раніше.
    - **Dependencies**: FR-4.

14. **FR-14**: При `extra='allow'` кожен ключ, що не заповнив поле, потрапляє і в `model_extra`, як у pydantic, і в `elastic_extra`.
    - **Priority**: Medium
    - **Rationale**: Розбіжність 34; рішення автора 2026-10-15 — реалізувати паритет.
    - **Dependencies**: FR-11. Без нього такий ключ під час перевірки заповнив би поле — verified via: прогін проби, `elastic_is_valid()` → `(True, [])` і `validated.id == 'N'` для забороненого ключа, 2026-10-15.

15. **FR-15**: За підсумком огляду механізмів pydantic (Prior Art) мертвий перелік `_SYSTEM_ATTRS` видаляється, а README точно описує валідатори класу вкладених моделей. `elastic_create` будує вкладену модель сам і передає готовий частковий екземпляр у поле, а pydantic запускає на будь-якому екземплярі в полі `@model_validator(mode='wrap')` і `mode='after'`. Тому такі валідатори вкладеної моделі спрацьовують на частковому екземплярі, а `field`- і `before`-валідатори — ні.
    - **Priority**: Medium
    - **Rationale**: вимога автора 2026-10-17 «не вигадувати велосипед»; огляд не знайшов публічної заміни власних механізмів без зміни звичайного шляху pydantic (рішення автора 2026-10-18 — лишити власний обхід). Охоронний тест виявив, що README («валідатори не запускаються») неточний для вкладених моделей. Еталон — `model_validate` з екземпляром з `model_construct` у полі: `['wrap', 'after']` на pydantic 2.11.7 і 2.14.1 — verified via: проба й тест, 2026-10-18.
    - **Dependencies**: FR-7 (місце 16).

### Non-Functional Requirements

1. **NFR-1**: Сумісність — зміни не ламають наявний тестовий набір; поточні 29 тестів проходять і після змін. Узгодження аліасів з pydantic (FR-4) цієї вимоги не порушує: жоден із 29 тестів не подає ім'я аліасованого поля без ключів конфігу — verified via: `grep -n "alias" tests/` і читання `tests/test_elastic_model.py:445-450`, `tests/test_basemodel_shallow_prebuild.py:53-64`, 2026-10-14. Змінюється лише випадок без ключів у тесті, який додала сама EM-1.
2. **NFR-2**: Продуктивність — механізм перехоплення не виконує жодного коду при успішному читанні наявного поля. Вимога структурна, а не вимірювана бенчмарком.
3. **NFR-3**: Зрозумілість — повідомлення нової помилки називає поле і причину, тобто розробник розуміє, що сталося, без читання джерельного коду.
4. **NFR-4**: Версіонування — зміна публічної поведінки відображена в номері версії пакета.

### Technical Constraints

- **Код уже вимагає pydantic 2.11**, тому нижня межа залежності не є предметом вибору: `model_validate` з потрібними аргументами з'явився саме там.
- **Перехоплення читання має обходитися без переліку службових імен** — мертвий `_SYSTEM_ATTRS` не задіюється.
- **Механіку відсутності поля вже задано кодом**: при `defaults=False` незавантажене поле фізично видаляється з інстансу, тому нова помилка має спиратися на цей факт, а не вводити паралельний облік.
- **Сховище невідомих полів отримує кожен вхідний ключ, який конфіг не дозволяє зіставити з полем**, зокрема заборонений аліас чи заборонене ім'я поля. Такий ключ не можна передавати в `model_construct`: той приймає і ім'я поля, і аліас безумовно, навіть при `validate_by_alias=False`, тобто заповнив би поле в обхід конфігу — verified via: прогін проби, 2026-10-14.
- **Не змінювати семантику `elastic_is_loaded` щодо дефолтів**: дефолт не вважається завантаженим, і це закріплено тестом.
- **Ключ, що збігається з іменем чи аліасом поля, не можна передавати в `model_construct` і при `extra='allow'`** (FR-14): той заповнив би ним поле. У `model_extra` такий ключ дописується після побудови моделі.
- **Облік завантажених полів не зберігається, а обчислюється** (FR-10). Жодна зміна не повинна знову класти в приватні атрибути стан, який відрізняється для моделей з однаковими даними: pydantic порівнює приватні атрибути в `==`.

## Out of Scope

- **Решта теми внутрішнього стану** — у scope втягнуто лише чотири речі, перелічені у FR-5.
- **Взаємний вплив прапорців валідації** — суворий режим зараз перемагає вимкнену валідацію, що суперечить власному докстрінгу (`gostmodels/elastic_model.py:521` vs `:226-227`).
- **Читання значень за `validation_alias`, `AliasChoices`, `AliasPath`** — поле з `Field(validation_alias="_v")` pydantic заповнює з `{'_v': 'x'}`, а `elastic_create` кладе значення у сховище невідомих полів — verified via: прогін проби, 2026-10-14. README про це не згадує (рішення автора 2026-10-14). FR-13 прибирає лише обхід валідації й хибні правила ключів, а не додає підтримку `validation_alias`.
- **Помилка `elastic_create` зі шляхом поля й усіма помилками** (Розбіжність 38) — окрема фіча. README описує обмеження (рішення автора 2026-10-15).
- **Часткові дані в полях `Optional`, `Union` і дискримінованих `Union`** (Розбіжність 39; код-рев'ю 2026-10-15, зауваження 3) — `elastic_create` таких полів не будує, і параметри конструктора до них не доходять. README описує обмеження (рішення автора 2026-10-15). Спроба 2026-10-17 віддати цей обхід pydantic зламала звичайний шлях (Prior Art), тож обмеження лишається.
- **Рядок усередині вбудованого generic на Python 3.10** (`children: list["Node"]`, `dict[str, "X"]`) — `elastic_create` падає з `PydanticUserError`, хоча `model_validate` того самого класу працює. Python 3.10 офіційно не підтримується (FR-6). Обхід — `List["Node"]` з `typing` або `from __future__ import annotations`. README описує обмеження з прикладом (рішення автора 2026-10-17).
- **Облік поля, чиє ім'я прийшло забороненим ключем, у моделі з валідації pydantic** (проба 2026-10-16). Йдеться про модель, створену конструктором чи `model_validate`, при `extra='allow'`. Якщо ключ з іменем аліасованого поля заборонений конфігом, pydantic кладе його і в `model_extra`, і в `model_fields_set`. Тому `elastic_is_loaded` повертає `True` для поля з дефолтом — verified via: прогін проби на pydantic 2.11.7, 2026-10-16. Зі стану моделі цей випадок не відрізнити від поля, заповненого аліасом, коли ім'я програло аліасу. Виправити можна лише зміною `model_fields_set`, а це розходження з pydantic. `elastic_create` і `elastic_get_validated_model` цього обмеження не мають. README описує обмеження (рішення автора 2026-10-16).
- **Виправлення докстрінга `elastic_create`**, який рекламує користувачу приватне поле (`gostmodels/elastic_model.py:238`) — той самий клас дефекту, що FR-7, але в іншому файлі.
- **Новий функціонал `ElasticModel`** — друга мета автора. Цей PRD лише готує для неї базу.
