## Передумови прогону

Запуск — **лише** `python -m pytest` із кореня проєкту. Bare `pytest` падає з `ModuleNotFoundError: No module named 'gostmodels'`, бо пакет у venv не встановлений, а конфігурації pytest у проєкті немає — verified via: `venv/bin/pytest tests/ -q` → 2 errors during collection, 2026-10-12. Дизайн виправляє це додаванням шляху імпорту в конфігурацію; доки це не зроблено, усі докази нижче читати як `python -m pytest`.

doctest'и вимагають `email-validator` (через `EmailStr` в обох прикладах). Для розробника його дає `requirements.txt:3`; для оточень із чистого встановлення це окрема залежність.

## Intentional Gaps

Чесний перелік того, чого цей план не покриває.

- **Текст повідомлень помилок у doctest'ах** — `IGNORE_EXCEPTION_DETAIL` ігнорує текст повідомлення (ім'я класу він порівнює, це перевірено). Прапорець потрібен, щоб у README стояло коротке ім'я помилки замість повного шляху модуля. Покрито натомість юніт-тестом 2.6, і лише для однієї помилки — текст інших документованих виключень не перевіряється нічим.
- **Межі гарантії 2 і 3 не виправляються, а фіксуються.** Тести 2.7a асертять поточну поведінку (поле, що затінює атрибут класу, повертає атрибут; дефолт при `defaults=True` читається), щоб документована межа лишалася правдивою. Це перевірка документації, не виправлення поведінки.
- **Обчислювані поля** — поза scope PRD. Поведінка конструктора на моделі з `@computed_field` лишається зламаною, тесту немає. Правиться лише формулювання в README.
- **Прогін на Python 3.10 із патчем** поки перевірений тільки делегованою оцінкою. Перед закриттям задачі потрібен live-прогін у головній сесії: інакше доказ 6.2 спирається на чужий звіт.
- **Бенчмарк для NFR-2 не робиться.** Вимога структурна — механізм не виконує коду на успішному читанні, — і перевіряється лічильником викликів (2.5), а не вимірюванням часу. Числового порога немає навмисно.
- **Негативна перевірка самої doctest-перевірки (1.5)** — одноразова, у постійний набір не входить. Без неї невідомо, чи перевірка справді ловить розходження, але тримати в наборі навмисно зіпсований вивід не можна.
- **Шість текстових місць README** (`code-only`) перевіряються чеклістом, не прогоном. Прогоном покритий лише підпис конструктора (4.1) — як найдорожчий дефект із цієї групи.
- **Другий приклад README** після переведення в doctest покривається повністю, але зараз його виводи перевірені лише делегованою оцінкою; у головній сесії вони не прогонялися.

## Verification Method Taxonomy

| Method | When to use |
|--------|-------------|
| `code-only` | No runtime test possible or needed: docs, config, `.md` prompt files, YAML, plain text |
| `auto-test` | An automated test suite can verify this: pytest, jest, go test, cargo test, phpunit |
| `manual-run-claude` | Claude executes a command and captures the output as evidence |
| `manual-run-user` | User runs a command or action and reports the result to Claude |
| `docker` | Verification requires a Docker container environment |
| `e2e` | End-to-end test via Playwright or test subagents |
| `observation` | Evidence is a claude-mem observation or search result |

### Live vs Simulated

Кожна не-`code-only` перевірка фіксує, була вона живою чи змодельованою:

- **`live`** — система справді виконувалася: реальна команда, реальний вивід, реальний побічний ефект. Очікування за замовчуванням.
- **`simulated`** — мок, стаб або сухий прогін замість реальної системи. Допустимо лише коли живий прогін дорогий, руйнівний або неможливий, і має бути сказано прямо.

Формат примітки в рядку задачі:

    → <підсумок> [live] (<дата>)
    → <підсумок> [simulated: <причина>] (<дата>)

**Хоча б один живий прогін має бути зроблений до позначки `[X]`.** Для цієї задачі це окремо важливо щодо доказу 6.2: делегована оцінка не рахується за живий прогін головної сесії.
